# 10. 학습 체크리스트 40문항

40개를 한 번에 풀 필요는 없다.

- 1회차: 3, 6, 7, 8, 10, 21, 23, 31, 36, 39번만 풀어 큰 그림 확인
- 2회차: 기초·코드 이해 20개
- 3회차: 설계·트레이드오프까지 전체 40개

먼저 답을 가리고 질문에 말로 답한 뒤 아래 해설과 비교한다. 막히면
[가장 쉬운 시작](./00-easy-start.md)의 해당 개념을 다시 읽는다.

영어로 된 이름은 실제 코드에서 쓰는 이름이라 남겼다. 답할 때는 영어를 외우기보다 “무슨 문제를
어떻게 해결하는 코드인지”를 한국어로 설명할 수 있으면 된다.

5. 비어 있는 cache와 값이 채워진 cache는 무엇이 다른가?
6. 진행 중인 같은 요청을 공유하지 않으면 어떤 중복 호출이 생기는가?
7. `Promise.all`과 동시에 실행할 개수를 제한하는 방식은 무엇이 다른가?
8. HTTP 호출 한 번의 시간 제한과 Tool 전체 종료 시간은 무엇이 다른가?
9. `AbortSignal`은 Promise를 어떻게 취소하는가?
10. 일부 데이터가 실패해도 성공한 결과를 남기는 것이 왜 중요한가?

# 정답과 해설

## A. 기초 해설

1. **Container 안에서 실행 중인 Node.js process의 메모리**에 있다. Container가 종료되면 함께 사라진다.
2. 저장 시간, 최대 개수, 오래 사용하지 않은 값부터 삭제하는 정책이 있다. 값이 없으면 외부 API를
   다시 호출한다.
3. Hit는 유효한 값을 즉시 재사용하는 경우이고, miss는 값이 없거나 만료돼 외부 API가 필요한 경우다.
4. TTL은 오래된 데이터 사용을 막고, LRU와 최대 개수는 메모리가 계속 커지는 것을 막는다.
5. 비어 있는 상태는 외부 API를 처음 호출해야 하고, 채워진 상태는 반복 요청에서 네트워크 조회를
   생략할 수 있다.
6. 저장 시간이 끝난 직후 동시 요청들이 모두 같은 외부 API를 반복 호출하는 현상이다.
7. `Promise.all`은 작업 시작 수를 제한하지 않는다. 현재 방식은 진행 중인 작업 수를 정해 나머지를
   대기시킨다.
8. Timeout은 HTTP 호출 한 번의 제한이고, 전체 종료 시각은 장소 검색·데이터 조회·재시도를 모두
   포함한 Tool 전체의 제한이다.
9. Signal은 취소 이벤트를 전달한다. Fetch처럼 이를 지원하는 작업이 듣고 실제 I/O를 중단해야 한다.
10. 네 API 중 하나의 장애가 이미 성공한 세 API의 유용한 결과까지 없애지 않게 하기 위해서다.

## B. 코드 해설

11. `assess-accessible-visit.tool.ts`의 `validateDestinationInput()`이다.
12. `performance-config.ts`의 `maxDestinations: 5`, `destinationConcurrency: 2`다.
13. 앞뒤 공백 제거, 연속 공백을 한 칸으로 축약, 한국어 locale 기준 소문자 key 비교다. 내부 공백을
    하지 않는다.
14. 작업이 받은 원래 `index` 위치인 `results[index]`에 결과를 저장한다.
15. Factory Promise에 붙인 `.finally(() => this.inFlight.delete(key))`다.
16. `KoreaTourAccessibilityAdapter.searchDestination()`의 `normalizeCacheKey()`가 만든다.
17. KMA `nx`, `ny`, `baseDate`, `baseTime`, `visitDate`다.
18. `dateIndexLoader`에서 방문일 목록을 먼저 찾는다. 없으면 `datasetLoader("nationwide")`에서 전국
    데이터를 가져오고 날짜로 거른 결과를 방문일별 목록에 저장한다.
19. `assess-accessible-visit.tool.ts`의 `compactBatchResult()`다.
20. 전체 시간, 후보 수, 장소 확정과 API 응답 시간, 외부 호출·cache·요청 공유·재시도·시간 초과·부분
    결과·데이터 상태를 `console.error`, 즉 stderr로 출력한다.

## C. 설계 해설

21. LLM과 MCP Host가 여러 형태를 한 항목에서 고르는 방식보다 명확한 두 입력 항목을 안정적으로
    만들 수 있기 때문이다.
22. 기존 다섯 Tool 유지, Host 선택 복잡도 감소, 단일 호출 하위 호환을 위해 기존 종합 Tool을
    확장했다.
23. Tool 호출은 줄어도 5×4개의 데이터 조회가 동시에 시작돼 외부 API의 순간 부하와 p99를 악화시킬
    수 있기 때문이다.
24. 후보 사이는 작업 수를 제한해야 하지만 한 후보의 네 데이터는 독립적이므로 동시에 조회해야
    응답 시간이 불필요하게 더해지지 않는다.
25. 좌표별 key는 다시 쓰일 가능성이 낮지만 전국 데이터는 모든 장소가 공유하고 메모리에서 하는
    거리 계산은 네트워크 조회보다 빠르기 때문이다.
26. 같은 contentId/address/coordinates를 재사용해 searchKeyword 중복과 불일치를 막기 위해서다.
27. 안쪽 단계마다 새 2.7초를 시작하지 않고 모두 같은 남은 시간을 계산하게 하기 위해서다.
28. 장애 중 외부 호출과 p99가 크게 늘어나는 것을 막으면서 짧은 일시적 오류만 회복하기 위해서다.
29. 관련 데이터 모델과 Tool 계약 전체를 바꾸지 않고 기존 `FAILED`, 주의사항, 시간 초과 로그로
    목적을 달성할 수 있었기 때문이다.
30. 기존 단일 응답 형식은 유지하고 여러 장소 응답에서만 반복 항목을 제거하기 위해서다.

## D. 트레이드오프 해설

31. 사용자 상태를 저장하지 않고, cache에 값이 없으면 항상 원래 API로 다시 계산할 수 있어 기능이
    이전 요청에 의존하지 않기 때문이다.
32. 각 서버의 cache가 따로이므로 최소 한 번씩, 즉 두 번 호출될 수 있다. 요청이 어느 서버로 가는지와
    저장 시간에 따라 더 늘 수도 있다.
33. 첫 요청들이 외부 API 응답을 기다리므로 느려지지만 기능 오류는 없다. Cache에 값이 없을 때 외부
    API를 호출하는 것이 정상 경로다.
34. 여러 서버가 값을 공유하고 한 곳에서 만료 처리할 수 있다. 대신 Redis 통신, 데이터 변환,
    운영·인증·장애 처리 비용이 생긴다.
35. Entry마다 배열/object 크기가 다르며 현재는 entry 개수만 제한하고 heap byte를 측정하지 않기
    때문이다.
36. 같은 `Promise`가 최초 요청의 취소 신호를 사용하므로 함께 기다리던 요청도 실패할 수 있다. 상위
    service는 부분 결과로 처리하고, 목록이 정리된 뒤 다음 요청은 다시 시도할 수 있다.
37. 순간 연결 수와 API 호출 한도 초과, 매우 느린 요청 증가를 막아 전체 처리량과 안정성을 높이는
    것이 더 중요하기 때문이다.
38. Kakao p99 3초 안에 응답하고 늦은 비핵심 데이터 하나가 전체 서비스를 붙잡지 않게 해야 하기
    때문이다.
39. 가짜 지연 시간에는 실제 네트워크, 공공 API 대기열, DNS/TLS 연결, 응답 크기, 운영 중 자원 경쟁이
    없고 표본도 작기 때문이다. 호출 수가 줄어드는 구조만 확실한 결과로 봐야 한다.
40. 서버별 차단 기준 조정, 만료 데이터라는 새 공개 상태, 백그라운드 갱신의 복잡도가 현재 효과보다
    컸다. 특정 API의 장기 장애와 만료 데이터 활용 필요가 운영 지표로 확인될 때 도입한다.
