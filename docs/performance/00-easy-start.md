# 가장 쉬운 시작: 보폭 성능 개선을 한 번에 이해하기

이 문서는 상세 문서를 읽기 전에 보는 입문편이다. 처음에는 클래스 이름을 외우지 않아도 된다.
먼저 **무슨 문제가 있었고, 어떤 원리로 해결했는지**만 잡자.

## 1. 이번 작업을 한 문장으로 말하면

> 여러 관광지를 한 번에 안전하게 조회하고, 같은 공공데이터를 반복 호출하지 않으며, 느린 API
> 하나가 전체 답변을 망치지 않도록 바꾼 작업이다.

이를 위해 여섯 가지 장치를 함께 사용했다.

1. **여러 장소 묶음 처리(batch)**: 관광지 여러 개를 Tool 한 번으로 받는다.
2. **결과 임시 저장(cache)**: 이미 받은 데이터는 잠시 재사용한다.
3. **진행 중 요청 공유(single-flight)**: 같은 데이터의 동시 요청은 외부 호출 하나를 함께 기다린다.
4. **동시 처리 제한**: 관광지를 최대 두 개씩 처리한다.
5. **전체 종료 시간과 취소**: 전체 작업을 2.7초 안에 끝내고 늦은 HTTP 요청을 중단한다.
6. **부분 결과**: 일부 API가 실패해도 성공한 정보는 반환한다.

### 자주 나오는 용어부터 간단히 보기

| 용어        | 이 문서에서의 쉬운 뜻                                         |
| ----------- | ------------------------------------------------------------- |
| Host        | 어떤 MCP Tool을 호출할지 결정하는 ChatGPT/Kakao 쪽 실행 주체  |
| Destination | 검색으로 확정된 관광지 정보 묶음: 이름, contentId, 주소, 좌표 |
| Source      | 접근성·날씨·충전소·축제처럼 결과를 구성하는 데이터 종류       |
| 외부 API    | 보폭 서버가 호출하는 공공 API                                 |
| Adapter     | 외부 API를 호출하고 그 결과를 보폭 내부 형식으로 바꾸는 코드  |
| Candidate   | Host가 비교 대상으로 전달한 관광지 후보 하나                  |
| 응답 시간   | 요청 하나가 끝날 때까지 걸린 시간                             |
| 처리량      | 일정 시간 동안 처리할 수 있는 요청 수                         |
| p99         | 요청 약 100개 중 99개가 이 시간 안에 끝난다는 지표            |
| 대체 처리   | Cache가 없거나 실패했을 때 원래 외부 API를 다시 조회하는 경로 |

## 2. 기존에는 어떤 문제가 있었나

사용자가 이렇게 물었다고 하자.

```text
"서울에서 휠체어로 갈 만한 곳 5개를 비교해줘."
```

Host LLM이 관광지 5개를 골라도 기존 Tool은 `destination` 하나만 받을 수 있었다.

```text
경복궁  → Tool 1회
창덕궁  → Tool 1회
덕수궁  → Tool 1회
경희궁  → Tool 1회
종묘    → Tool 1회
```

각 Tool은 다시 장소 검색, 접근성, 날씨, 충전소, 축제를 조회했다. 같은 종로구 충전소와 전국 축제
데이터도 후보마다 반복해서 받을 수 있었다.

특히 축제 조회가 비쌌다.

```text
관광지명과 주소로 빠른 검색 1~2회
↓ 결과가 없으면
전국 축제 데이터를 100건씩 여러 페이지 조회
```

게다가 HTTP 한 번의 timeout은 있었지만 **Tool 전체가 언제까지 끝나야 하는지**는 정해져 있지
않았다. 축제 API가 늦으면 이미 날씨와 접근성 조회가 끝났어도 전체 응답이 늦어질 수 있었다.

## 3. 개선 후에는 어떻게 달라졌나

이제 종합 Tool은 두 가지 방식으로 호출할 수 있다.

```typescript
// 한 장소
{ destination: "경복궁", ... }

// 여러 후보 비교
{ destinations: ["경복궁", "창덕궁", "덕수궁"], ... }
```

둘 중 하나만 쓸 수 있고 후보는 최대 5개다. 기존 단일 호출은 그대로 동작한다.

여러 후보가 오면 다음 순서로 처리한다.

```text
입력 검사
↓
공백 정리와 중복 제거
↓
후보를 두 개씩 처리
↓
각 후보의 장소를 한 번 확정
↓
접근성·날씨·충전소·축제를 병렬 조회
↓
2.7초 안에 모인 결과를 조합
↓
일부 실패가 있어도 사용 가능한 결과 반환
```

## 4. 핵심 개념을 순서대로 이해하기

### 4.1 여러 장소 묶음 처리: Tool 호출을 다섯 번에서 한 번으로

기존 방식은 장소 5개를 평가하려면 종합 Tool도 5번 호출했다. 여러 장소 묶음 처리는 후보를 한
배열에 담아 Tool 한 번으로 전달한다. 하지만 Tool 호출만 합치고 내부 API를 모두 동시에 시작하면
순간 부하는 그대로다. 그래서 묶음 처리와 동시 처리 제한을 함께 사용한다.

### 4.2 Cache: 이미 받은 결과를 일정 시간 재사용하기

경복궁 정보를 방금 공공 API에서 받았다면 바로 다음 요청에서 다시 인터넷으로 가져올 필요가
없다. Node process의 메모리에 잠시 보관하고 재사용한다.

```text
Cache hit  → 저장된 값을 바로 사용
Cache miss → 외부 API 조회 후 저장
```

단순한 `Map`과 달리 현재 cache에는 두 가지 안전장치가 있다.

- **TTL**: 일정 시간이 지나면 오래된 값으로 보고 사용하지 않는다.
- **최대 저장 개수 + LRU**: 정해진 개수를 넘으면 가장 오래 사용하지 않은 값을 버린다.

예를 들어 날씨는 자주 바뀌므로 10분만 재사용하고, 관광지 검색 결과는 비교적 안정적이어서
24시간 재사용한다.

### 4.3 Stateless인데 메모리를 써도 괜찮나

괜찮다. 중요한 기준은 **메모리가 사라져도 정답을 다시 계산할 수 있는가**다.

보폭 cache에는 로그인 정보나 사용자 선택을 저장하지 않는다. Cache가 없으면 원래 공공 API를
다시 호출한다. Container가 재시작돼 cache가 전부 사라져도 첫 요청이 조금 느려질 뿐 기능은
정상이다.

Container가 여러 개면 각 container가 자기 cache를 가진다. A container가 경복궁을 기억해도 B는
모를 수 있다. Redis처럼 실행 중인 모든 서버가 공유하지는 않지만, 각 process 안의 반복 호출은
줄어든다.

### 4.4 진행 중 요청 공유: 같은 외부 조회를 한 번만 실행하기

Cache만으로는 다음 상황을 막지 못한다.

```text
동시에 10명이 경복궁 요청
↓
아직 cache가 비어 있음
↓
10명 모두 외부 API 호출
```

Single-flight는 첫 요청이 만든 진행 중 Promise를 Map에 넣는다.

```text
첫 요청 → 외부 API 호출 → Promise 저장
나머지 9개 → 같은 Promise를 기다림
결과 도착 → 모두 같은 결과 사용
```

외부 API는 가능한 한 한 번만 호출된다. 성공하면 결과를 cache에 넣고, 실패해도 `finally`에서
진행 중 Promise를 반드시 삭제한다. 그래야 다음 요청이 과거의 실패 Promise에 영원히 묶이지 않는다.

### 4.5 동시 처리 제한: 관광지를 두 개씩 처리하기

후보가 5개라고 모두 동시에 시작하면 다음처럼 순간 부하가 커질 수 있다.

```text
5개 후보 × 4가지 데이터 = 최대 20개 조회 작업
```

현재는 후보를 동시에 처리하는 작업을 2개만 둔다.

```text
1차: 경복궁 + 창덕궁
2차: 덕수궁 + 경희궁
3차: 종묘
```

후보 하나 안의 접근성·날씨·충전소·축제는 서로 독립이므로 병렬 실행한다. 즉 **후보 사이는 두
개로 제한하고, 한 후보 안의 독립 조회는 병렬화**한다.

이 방식은 모든 후보를 한꺼번에 실행하는 것보다 조금 느릴 수 있다. 대신 공공 API의 순간 부하와
p99 응답 시간이 갑자기 커지는 것을 막는다.

### 4.6 HTTP 호출 제한과 Tool 전체 종료 시간

- HTTP timeout: 외부 API 한 번을 얼마나 기다릴지
- Tool 전체 종료 시간: 장소 검색부터 결과 조합까지 전체를 언제 끝낼지

현재 값은 HTTP 한 번 최대 900ms, Tool 전체 2.7초다.

```text
전체 종료 시간: 2.7초
이미 사용한 시간: 2.2초
남은 시간: 0.5초
```

이 시점의 새 HTTP 요청은 900ms를 전부 쓸 수 없고 남은 시간 안에서만 실행된다. 재시도할 시간도
부족하면 시작하지 않는다.

전체 종료 시각이 오면 `AbortSignal`이 HTTP client까지 전달돼 진행 중인 `fetch`를 실제 중단한다.
사용자에게 먼저 응답한 뒤 네트워크 작업을 계속 남겨두지 않는다.

### 4.7 부분 결과: 성공한 정보는 유지하기

다음 상황을 생각해 보자.

```text
접근성  SUCCESS
날씨    SUCCESS
충전소  SUCCESS
축제    TIMEOUT → 현재 응답 상태로는 FAILED
```

보폭은 앞의 세 결과를 버리지 않는다. 축제는 확인하지 못했다고 주의 문구를 붙이고 종합 상태를
`CHECK_REQUIRED`로 만든다. 여러 장소 요청에서는 이런 후보가 있으면 전체 상태가
`PARTIAL_SUCCESS`가 될 수 있다.

외부 시스템 네 개가 모두 정상이어야만 응답하는 구조보다 실제 서비스 가용성이 높아진다.

### 4.8 축제 최적화: 전국 데이터를 한 번 받고 여러 장소가 같이 쓰기

기존의 빠른 검색은 결과가 없는 경우가 많았고, 그 뒤 전국 데이터를 다시 받았다. 개선 후에는
전국 데이터를 기본 1,000건씩 받아 6시간 cache한다.

```text
전국 축제 데이터
↓ 방문일로 한 번 거른 축제 목록
↓ 관광지 좌표별 거리 계산
```

같은 날짜의 서울 관광지 5개는 전국 데이터와 날짜별 목록을 공유한다. 오래 걸리는 네트워크
다운로드는 공유하고 비교적 빠른 거리 계산만 장소별로 수행한다.

### 4.9 재시도: 아무 실패나 다시 시도하지 않기

재시도 대상은 일시적일 가능성이 있는 실패뿐이다.

```text
재시도 가능: 429, 502, 503, 504, 네트워크 오류, 시간 초과
재시도 안 함: 400, 401, 403 등
최대 횟수: 1회
```

재시도 전에는 40ms를 기준으로 짧게 기다리고 작은 무작위 시간을 더한다. 전체 남은 시간이
부족하면 재시도하지 않는다. 서버가 긴 `Retry-After`를 주면 너무 일찍 다시 호출하지 않고 현재
요청에서는 재시도를 포기한다.

## 5. 실제 요청 하나를 끝까지 따라가기

다음 요청을 예로 보자.

```json
{
  "destinations": ["경복궁", " 경복궁 ", "창덕궁"],
  "visitDate": "2026-08-08",
  "travelerType": "POWER_WHEELCHAIR"
}
```

### 1단계: MCP 입력 검사

`assessAccessibleVisitInputSchema`가 날짜, traveler type, 배열 길이를 검사한다.
`validateDestinationInput()`은 `destination`과 `destinations` 중 정확히 하나만 있는지 확인한다.

### 2단계: 정규화와 중복 제거

`VisitAssessmentService.assessBatch()` 안의 `normalizeDestinations()`가 앞뒤 공백과 연속 공백을
정리한다. 따라서 두 경복궁은 하나가 되어 실제 후보는 2개다.

### 3단계: 전체 시계 시작

2.7초 뒤의 `deadlineAtMs`와 `AbortSignal`을 만든다. 이 요청 실행 정보는 외부 데이터 조회 코드와
HTTP client까지 전달된다.

### 4단계: 후보 두 개 처리

`mapWithConcurrency()`의 limit가 2이므로 경복궁과 창덕궁을 함께 시작할 수 있다.

### 5단계: 장소 확정

각 후보는 `DestinationResolver.resolve()`를 호출한다. Tourism adapter의 `CachedLoader`가 cache와
진행 중 Promise를 확인하고 필요한 경우에만 `/searchKeyword2`를 호출한다.

확정된 `Destination`에는 `contentId`, 주소, 위경도가 있다. 이후 네 service가 같은 객체를 공유한다.

### 6단계: 네 가지 데이터 조회

후보별 `assessResolvedDestination()`이 `Promise.allSettled`로 네 service를 호출한다.

- 접근성: `contentId` cache
- 날씨: 기상청 격자와 발표 시각별 cache
- 충전소: 시도·시군구별 cache
- 축제: 방문일별 목록과 전국 데이터 cache

### 7단계: 실패와 재시도 처리

HTTP가 일시적으로 실패하고 시간 여유가 있으면 최대 한 번 재시도한다. 전체 종료 시각이 오면
`fetch`를 취소한다. 한 데이터 조회의 실패는 해당 데이터의 `FAILED` 결과로 바꾼다.

### 8단계: 응답 조립

장소 후보별 평가를 유지하고 묶음 전체 상태를 계산한다. `compactBatchResult()`는 데이터 결과마다
반복되는 장소 객체를 제거해 응답 크기를 줄인다. 최종값은 MCP `structuredContent`로 반환된다.

## 6. 알아두어야 할 한계

이 구현이 해결하지 않은 것도 분명히 알아야 한다.

- 서버 메모리 cache는 실행 중인 서버끼리 공유되지 않는다.
- Cache entry 개수는 제한하지만 정확한 byte 크기까지 측정하지 않는다.
- 전국 축제 데이터를 처음 받는 조회는 여전히 느릴 수 있다.
- Single-flight 최초 요청이 abort되면 같은 Promise를 기다리던 요청도 실패할 수 있다.
- Deadline 때문에 느리지만 정상인 API를 포기할 수 있다.
- 응답의 `FAILED`만으로 시간 초과와 5xx를 구분하지 못하며 요약 로그로 원인을 본다.
- 장애 API 임시 차단과 만료 데이터 재사용은 이번에 구현하지 않았다.
- 모의 성능 테스트 수치는 실제 운영 p99가 아니다.

이 한계가 있어도 cache가 없어도 기능이 동작하고, 배포 구조가 작으며, p99 3초 목표를 지켜야 하는
현재 대회 환경에는 합리적인 선택이다.

## 7. 로컬과 운영 환경은 어떻게 다른가

애플리케이션 코드는 둘 다 `process.env`만 본다.

```text
LOCAL
.env → node --env-file → process.env → createContainer

PRODUCTION
PlayMCP/container env injection → process.env → createContainer
```

코드에서 `.env`를 읽는 `dotenv`는 추가하지 않았다. `.env`와 API key를 Docker image에 넣지도
않는다. 로컬 Docker는 `docker run --env-file .env ...`로 실행할 때 값을 전달한다.

## 8. 성능은 정확히 어디에서 좋아지나

| 장치           | 가장 큰 효과                                | 주의점                             |
| -------------- | ------------------------------------------- | ---------------------------------- |
| 여러 장소 묶음 | Host Tool 호출 감소                         | 내부 동시 처리 제한이 함께 필요    |
| Cache          | 값이 있을 때 응답 시간과 반복 API 호출 감소 | 재시작·서버별로 처음엔 비어 있음   |
| 진행 요청 공유 | 동시에 들어온 같은 API 호출 감소            | 공유 Promise 실패도 함께 전달      |
| 동시 처리 2개  | 순간 부하와 매우 느린 요청 감소             | 묶음 요청이 조금 느려질 수 있음    |
| 축제 공유      | 전국 데이터 다운로드 감소                   | 첫 조회 비용은 남음                |
| 종료·취소      | p99 상한과 네트워크 자원 회수               | 느린 정상 데이터를 포기 가능       |
| 부분 결과      | 전체 기능 이용 가능성 향상                  | 확인 못 한 항목을 알려야 함        |
| 제한 재시도    | 일시적 오류 회복                            | 호출과 응답 시간이 조금 늘 수 있음 |

## 10. 1분 설명 예시

> 기존 보폭 MCP는 관광지 후보마다 Tool을 따로 호출했고, 같은 축제나 충전소 데이터도 반복 조회할
> 수 있었습니다. 그래서 기존 종합 Tool이 최대 5개 장소를 한 번에 받고 두 장소씩 처리하게
> 바꿨습니다. 반복 데이터는 저장 시간과 최대 개수가 정해진 서버 메모리 cache에 넣고, 같은 조회가
> 진행 중이면 그 `Promise`를 함께 기다립니다. 전체 요청은 2.7초 안에 끝내고 실제 HTTP 요청도
> 취소합니다. 한 API가 실패해도 성공한 접근성·날씨 결과는 유지합니다.
> Cache가 사라져도 원래 API를 다시 호출하므로 기능이 이전 요청 상태에 의존하지 않습니다.

## 11. 자주 받는 질문

### “Redis가 더 좋은 것 아닌가요?”

여러 서버의 값 공유만 보면 Redis가 더 강하다. 하지만 Redis까지의 네트워크 통신, 별도 운영,
인증과 장애 처리가 추가된다. 현재 대회는 외부 운영 시스템 없이 하나의 image로 실행해야 하고
cache가 없어도 동작하므로 서버 내부 cache가 더 작은 해법이다.

### “Tool 한 번이면 왜 동시 처리 제한이 필요한가요?”

Tool 횟수와 외부 API 동시 호출 수는 다른 문제다. Tool 한 번 안에서도 후보 5개×데이터 4개를
동시에 시작할 수 있기 때문에 내부 제한이 필요하다.

### “TTL이 끝나면 사용자는 오류를 받나요?”

아니다. 만료된 값을 지우고 외부 API를 다시 호출한다. 외부 API까지 실패하면 그 데이터만
`FAILED`가 될 수 있다.

### “Tool 전체 종료 시간과 HTTP 제한 중 하나만 있으면 안 되나요?”

안 된다. HTTP 호출별 제한만 있으면 여러 단계의 시간이 계속 더해진다. Tool 전체 종료 시간만 있고
실제 요청 취소가 연결되지 않으면 사용자에게 응답한 뒤에도 HTTP 작업이 계속 실행될 수 있다.

### “왜 시간 초과 상태를 공개 결과값에 추가하지 않았나요?”

기존 데이터 모델과 다섯 Tool의 입력·출력을 넓게 변경하지 않기 위해 `FAILED`와 주의사항을
재사용했다. 원인은 요약 로그의 시간 초과 횟수로 확인한다.

### “성능이 무조건 빨라졌나요?”

Cache에 값이 있는 요청, 반복·동시 요청, 여러 장소가 데이터를 공유하는 경우에는 빨라진다. Cache가
비어 있는 단일 요청은 외부 API 응답 시간을 그대로 기다린다. 동시 처리 제한 때문에 일부 묶음
요청은 모든 작업을 한꺼번에 시작할 때보다 느릴 수도 있다. 목표는 평균 속도뿐 아니라 외부 API
중복 호출과 p99 불안정을 함께 줄이는 것이다.
