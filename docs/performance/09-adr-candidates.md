# 09. ADR 후보 초안

ADR은 중요한 설계 결정을 나중에도 이해할 수 있도록 남기는 문서다. 각 항목은 다음 네 부분으로
읽으면 된다.

- 상황: 어떤 문제가 있었는가
- 결정: 무엇을 선택했는가
- 다른 방법: 무엇을 함께 검토했는가
- 결과: 무엇이 좋아지고 어떤 한계가 생겼는가

## ADR-001: 서버 내부에 크기가 제한된 cache 사용

### 상황

관광지 검색, 접근성, 지역 충전소, 기상청 격자 예보, 전국 축제 데이터가 반복 조회됐다. 대회
배포에서는 단일 Docker image와 외부 환경변수 주입을 유지해야 하며 Redis와 DB를 쓰지 않는다.
Cache가 사라졌다고 기능이 실패하거나 사용자 상태가 사라지는 구조여서는 안 된다.

### 결정

Node.js process 안에 저장 시간, 최대 개수, 오래 사용하지 않은 값 삭제 기능이 있는
`BoundedTtlCache`를 둔다. 데이터 종류별 `CachedLoader`가 이를 사용한다. 값이 없거나 cache 오류가
나면 기존 외부 API를 호출한다. 데이터별 저장 시간과 key는 `performanceConfig`에서 관리한다.

### 함께 검토한 방법

- Redis/distributed cache
- 무제한 Map
- Cache 없음
- DB snapshot/정기 ETL

### 결과와 한계

저장된 값의 응답 시간과 반복 API 호출이 줄고 새 운영 인프라도 필요 없다. 반면 재시작 뒤에는
cache가 비어 있고 여러 서버가 값을 공유하지 않는다. 저장 개수만 제한하므로 정확한 메모리 byte
상한도 아니다. 그래도 cache가 없으면 외부 API를 다시 호출하므로 기능은 정상 동작한다.

## ADR-002: 기존 종합 Tool이 단일·복수 장소를 명확히 구분

### 상황

Host가 후보 N개를 만들면 단일 `destination` Tool을 N번 호출한다. `string | string[]` union은 LLM
parameter 생성 안정성을 떨어뜨릴 수 있고 새 Tool은 기존 다섯 Tool 정책과 선택 복잡도를 늘린다.

### 결정

`assess_accessible_visit`에 `destination?: string`, `destinations?: string[]` 두 property를 둔다. 정확히
하나만 허용하고 batch는 1~5개, batch와 contentId 동시 사용은 금지한다. 기존 단일 output은 유지하고
batch만 `results`를 사용한다.

### 함께 검토한 방법

- `destination: string | string[]`
- 새 `assess_accessible_visits` Tool
- Host가 계속 N번 호출
- contentId 배열까지 포함한 복합 batch

### 결과와 한계

Host의 Tool 호출과 반복 외부 조회가 줄고 기존 단일 호출도 그대로 동작한다. 대신 입력·출력 형태가
늘고 두 입력 항목 사이의 규칙을 handler에서 추가로 검사해야 한다.

## ADR-003: 장소 후보를 두 개씩 처리

### 상황

후보 5개를 Tool 하나로 합쳐도 모든 후보와 데이터를 `Promise.all`로 실행하면 20개 이상 작업이
동시에 시작될 수 있다. 하나씩 처리하면 외부 API에는 안전하지만 전체 응답 시간이 너무 길어진다.

### 결정

새 라이브러리 없이 `mapWithConcurrency`로 후보를 두 개씩 처리한다. 후보 하나 안의 독립된 네
데이터 조회는 `Promise.allSettled`로 동시에 실행한다. 제한값은 공통 설정에 둔다.

### 함께 검토한 방법

- 모든 candidate `Promise.all`
- 완전 순차
- `p-limit` dependency
- 데이터 종류별 전체 동시 호출 제한

### 결과와 한계

한꺼번에 시작되는 호출과 매우 느린 요청이 늘어나는 문제를 줄이면서 하나씩 처리하는 것보다는
빠르다. 모든 API가 빠를 때는 5개를 동시에 처리하는 것보다 느릴 수 있고, 서버 전체의 API 호출
한도를 보장하는 기능은 아니다.

## ADR-004: 전체 종료 시간, 요청 취소, 부분 결과

### 상황

HTTP 호출별 제한만으로 장소 검색과 여러 페이지 조회를 포함한 전체 Tool 시간을 제한할 수 없었다.
Kakao p99 3초 목표가 있고 한 데이터의 실패가 이미 얻은 나머지 결과까지 없애면 안 된다.

### 결정

Tool 시작 시 2.7초 뒤의 전체 종료 시각을 만들고 `OperationContext`로 취소 신호와 종료 시각을 외부
조회 코드와 HTTP client에 전달한다. HTTP 호출 한 번은 최대 900ms이며 전체 남은 시간을 넘지
못한다. 종료 시각이 오면 `fetch`를 취소하고, 기존 `Promise.allSettled`로 성공한 데이터는 유지하며
실패한 데이터만 `FAILED`로 표시한다.

### 함께 검토한 방법

- HTTP timeout만 사용
- `Promise.race`로 response만 끊고 HTTP는 background 유지
- 하나가 실패하면 전체 실패
- 5초 이상의 넉넉한 deadline

### 결과와 한계

매우 느린 요청과 응답 뒤에도 남는 네트워크 작업을 제한하고, 일부 장애가 있어도 정보를 제공한다.
대신 느리지만 정상인 응답을 포기할 수 있다. Tool의 `FAILED` 결과만으로 시간 초과와 5xx 오류를
구분하지 못하므로 성능 측정 로그가 필요하다.

## ADR-005: 전국 축제 데이터 공유

### 상황

관광지명과 주소로 한두 번 검색해도 결과가 없으면 전국 데이터를 100건씩 여러 페이지로 다시
받았다. 이 과정이 장소마다 반복됐다. 지역 조건 검색이 실제 주변 축제를 빠짐없이 찾는지도
확실하지 않았다.

### 결정

먼저 좁게 검색하는 경로를 제거한다. 전국 데이터는 한 페이지에 1,000건씩 받고 하나의 key로 6시간
저장한다. 방문일에 열리는 축제 목록은 날짜별로 최대 32개 저장하고, 각 요청에서는 장소와의 거리만
계산한다.

### 함께 검토한 방법

- 시도·시군구 조건 검색 개선
- 장소별 검색 결과 저장
- 전국 데이터를 DB에 저장하고 별도 작업으로 갱신
- 기존의 좁은 검색 후 전국 조회 유지

### 결과와 한계

여러 장소와 날짜 요청의 네트워크 호출이 크게 줄고 항상 같은 전국 데이터를 기준으로 검색한다.
다만 전국 데이터를 처음 받는 요청은 여전히 오래 걸릴 수 있고, 데이터 한 묶음의 정확한 byte
상한은 없다. 뒤에서 미리 갱신하거나 만료된 데이터를 임시로 반환하는 기능도 없다.

## ADR-006: 남은 시간을 확인하는 제한적 재시도

### 상황

일시적인 429·5xx·네트워크 오류는 한 번 더 시도하면 성공할 수 있다. 하지만 계속 재시도하면 p99가
길어지고 이미 장애가 난 외부 API의 부하도 커진다. 기존에는 `Retry-After` 값을 읽기만 했다.

### 결정

429·502·503·504, 시간 초과, 네트워크 오류만 최대 한 번 재시도한다. 기본 40ms에서 조금씩 늘어나는
대기 시간과 작은 무작위 값을 사용하며 최대 200ms다. `Retry-After`가 너무 길거나 전체 남은 시간이
부족하면 재시도하지 않는다.

### 함께 검토한 방법

- 재시도하지 않음
- 모든 5xx·4xx 응답 재시도
- 대기 시간을 늘리며 3회 이상 재시도
- 별도 대기열에서 비동기로 재시도

### 결과와 한계

짧은 일시적 오류의 성공률은 올라가지만 외부 호출 수와 응답 시간이 조금 늘 수 있다. 전체 남은
시간, 재시도 횟수, 허용된 HTTP 상태 목록으로 증가 폭을 제한한다.
